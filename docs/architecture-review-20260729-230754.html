Problem

Release preview 与 channel release delivery 分居 cron module 和 Telegram module；两处调用同一 GitHub、KV 与 Telegram adapter，interface 细节跨 seam 泄漏。

Solution

将 Release delivery 的选择、投递和状态推进收进一个 deep module；cron 与 Telegram command module 只触发该 module。

  • • locality：投递顺序集中
  • • leverage：两个 caller 复用行为
  • • interface 成为 test surface
  • • implementation 吸收协调细节
  • • deletion test：复杂度回到两 caller
  • • 无第二 adapter，不新增外部 seam

Problem

一个 154 行 dispatch function 同时决定 command flow、Subscription 生命周期和 Wiki flow；每项新增行为扩大 interface 认知负担，且 tests 无法只越过 Telegram update seam。

Solution

保持一个 Telegram update interface，将 command flow 留在 deep command module；仅当第二个 adapter 出现时，才把可变行为提升为真实 seam。

  • • locality：鉴权集中
  • • leverage：新增 command 不碰入口
  • • interface 成为 test surface
  • • implementation 吸收 reply 细节
  • • deletion test：流程散回入口
  • • 一个 adapter 仍是假设 seam

Problem

KV module 的小函数把 state-key、ETag 与移除时清理的协议暴露给两个 caller；目前 interface 接近 implementation，depth 较浅。

Solution

只在 Subscription state 的不变量开始增长时收拢其 implementation；先不为单一 KV adapter 扩大 seam。

  • • locality：状态不变量集中
  • • leverage：迁移键协议一次
  • • adapter 可替换于 tests
  • • interface 缩小至领域操作
  • • deletion test：协议回到 callers
  • • 现状规模使它仍 speculative

Problem

Solution

将 Snapshot rotation policy 收进 deep module，workflow 只启动该 module；外部调用保留为 implementation 内的 adapter。

  • • locality：轮换规则集中
  • • leverage：workflow 只学一个 interface
  • • tests 覆盖完整结果分类
  • • implementation 吸收 exit
  • • deletion test：规则回到 CLI
  • • 单一 Tencent adapter 不扩 seam

Top recommendation

先加深 Release delivery module

它已在 cron 与 Subscription 新增后的 Release preview 重复出现；一个 module 可把投递策略、状态与 tests 集中到同一 interface，带来最高 locality 与 leverage。
